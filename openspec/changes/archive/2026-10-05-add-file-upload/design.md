## Context

`ARCHITECTURE.md` §3 puts an S3-compatible store beside Postgres and says that if it writes
to either, it is `core`. Nothing in the repository has written to it yet, and the shape of
that first write decides more than it looks like it does.

The deciding constraint is the browser. `connect-web` has no client streaming, so a file
sent through a Connect RPC is a base64 field in a unary message: a third larger on the wire
and wholly in `core`'s heap. The alternative is a plain multipart `POST` route, which
`CLAUDE.md` forbids in as many words — `/auth/google/start`, `/auth/google/callback` and
`/auth/logout` are *the* one non-Connect browser surface, and the exception is written as
being about transport, not about convenience.

A presigned `PUT` satisfies both. The contract stays Connect, `core` never touches the
bytes, and the object store enforces the size limit at the edge.

It also creates the problem this design spends most of its length on: **`core` never sees
the file, so `core` knows nothing true about it.**

## Goals / Non-Goals

**Goals:** the `import_batches` table, its policy, the two RPCs that create and confirm a
batch, the object-store client, the measurement job, and the expiry job.

**Non-goals:** parsing, validation, persistence, deduplication, the upload screen. Named in
the proposal.

## The data model

**`import_batches` already exists.** Change 2.5's migration 007 creates it in the minimal
shape `transactions` needs to point at: `org_id`, `id`, `entity_id`, `source_kind`,
`status`, `created_at`, a primary key leading with `org_id`, a composite foreign key to
`entities`, and — already — `ENABLE` plus `FORCE ROW LEVEL SECURITY` with an
`import_batches_tenant` policy. Its `status` carries a `CHECK` admitting exactly one value,
`'persisted'`, and 007's own comment says why: "Change 2.1 adds the rest of the state
machine ... a `CHECK` admitting exactly one value makes widening it a visible edit rather
than a silent drift."

This change is that widening. It is an `ALTER`, not a `CREATE`, and it adds **no policy** —
007's is correct, and a second definition of one rule is how the two drift.

```sql
-- Every column below arrives NOT NULL with no default, which is only safe on an
-- empty table. 007 has not been deployed anywhere that persists a batch, so the
-- migration asserts that rather than assuming it: a non-empty table here means
-- somebody imported against a schema this change is about to move.
DO $$ BEGIN
  IF (SELECT count(*) FROM import_batches) > 0 THEN
    RAISE EXCEPTION 'import_batches is not empty; change 2.1 assumes it has never been written';
  END IF;
END $$;

ALTER TABLE import_batches
    -- users is global and outside RLS (ARCHITECTURE.md 5.5). A plain reference is
    -- right here for the same reason memberships carries one: the target is not
    -- tenant data, so the check discloses nothing about another tenant.
    ADD COLUMN uploaded_by    uuid NOT NULL REFERENCES users (id) ON DELETE RESTRICT,

    -- What the browser asked for. Signing conditions, never facts; see D2.
    ADD COLUMN file_name      text   NOT NULL CHECK (length(btrim(file_name)) > 0),
    ADD COLUMN declared_bytes bigint NOT NULL CHECK (declared_bytes > 0),
    ADD COLUMN declared_type  text   NOT NULL,

    -- The object key. Generated by core from org_id and id, never from file_name
    -- -- a user-supplied name is a path traversal and a collision at once.
    ADD COLUMN file_key       text   NOT NULL,

    -- What core measured after reading the object back. NULL until then.
    ADD COLUMN file_sha256    bytea  NULL CHECK (file_sha256 IS NULL OR length(file_sha256) = 32),
    ADD COLUMN byte_length    bigint NULL CHECK (byte_length IS NULL OR byte_length > 0),
    ADD COLUMN content_type   text   NULL,

    -- Filled by later changes. 2.2 sets row_count; any stage may set
    -- failure_code, which is a code and never a sentence.
    ADD COLUMN row_count    integer NULL CHECK (row_count IS NULL OR row_count >= 0),
    ADD COLUMN failure_code text    NULL,

    ADD COLUMN upload_expires_at timestamptz NOT NULL,
    ADD COLUMN updated_at        timestamptz NOT NULL DEFAULT now();

-- Widening the state machine (design D3). 'persisted' is 007's single
-- placeholder and it is dropped rather than carried: it names the same state as
-- 'imported', and two names for one state is precisely the drift that narrow
-- CHECK existed to prevent. The table is empty, asserted above, so nothing is
-- migrated -- only redefined.
ALTER TABLE import_batches DROP CONSTRAINT import_batches_status_check;
ALTER TABLE import_batches ALTER COLUMN status DROP DEFAULT;
ALTER TABLE import_batches ADD CONSTRAINT import_batches_status_check CHECK (status IN (
    'awaiting_upload','abandoned','uploaded',
    'parsing','parsed','validating','validated','rejected',
    'persisting','imported','failed'));

-- A batch past the upload has been measured -- EXCEPT one that failed before it
-- could be, and that exception is load-bearing. An earlier draft of this design
-- omitted 'failed', and on PostgreSQL 16 that refused the exact upload_missing
-- row D2 describes:
--
--   ERROR:  new row violates check constraint "import_batches_measured_past_upload"
--   DETAIL: Failing row contains (failed, null, null, null).
--
-- A batch that failed AFTER measurement keeps its measurements; failure_code is
-- what distinguishes the two, not the nullity of these three columns.
ALTER TABLE import_batches ADD CONSTRAINT import_batches_measured_past_upload CHECK (
    status IN ('awaiting_upload','abandoned','failed')
    OR (file_sha256 IS NOT NULL AND byte_length IS NOT NULL AND content_type IS NOT NULL));

-- Scoped by org_id like every other uniqueness constraint, because
-- referential-integrity checks bypass row-level security (migration 00004,
-- design D1). The key embeds a random uuid, so two organisations cannot collide
-- in the bucket regardless of what this constraint scopes.
ALTER TABLE import_batches ADD CONSTRAINT import_batches_file_key_unique UNIQUE (org_id, file_key);

CREATE INDEX import_batches_status_idx ON import_batches (org_id, status, created_at DESC);
CREATE INDEX import_batches_entity_idx ON import_batches (org_id, entity_id, created_at DESC);
```

### What this change deliberately does not add

- **No row-level security statements.** 007 enables, forces and policies this table. The
  ordinary shape is already there and re-stating it would be a second definition of one
  rule.
- **No `UNIQUE (org_id, id, source_kind)`.** An earlier draft added it so that change 2.5
  could point a composite foreign key at it and make `transactions.source_kind` provably
  equal to its batch's. 007 solved the same problem with a `CONSTRAINT TRIGGER`
  (`txn_source_kind_matches_batch`), which needs nothing from this change. The constraint
  would now be redundant, and a redundant uniqueness constraint on a tenant table is not
  free — it is another index and another way to be surprised.
- **No composite foreign key to `entities`.** 007 has it.

## D1 — Presigned `PUT`, not bytes through `core`

**Rejected: a unary Connect RPC carrying the file.** base64 is a third larger on the wire,
the whole file lands in `core`'s heap, and the same bytes then have to be written to the
store anyway — two transfers instead of one.

**Rejected: a multipart `POST` route on `core`.** It is the cheapest thing to build and it
costs the one invariant that keeps the browser contract legible. `CLAUDE.md` states that
the `/auth` exception is about transport — an OIDC redirect cannot be an RPC — and not
about payload shape. An upload *can* be an RPC; it is simply a worse one.

**Chosen: `core` signs, the browser `PUT`s, `core` confirms.** `Content-Length` and
`Content-Type` are signed headers, so the store rejects a request that does not match what
was signed. The cost is D2.

## D2 — `core` never sees the bytes, so nothing the client says is a fact

Three numbers matter downstream: the SHA-256 (D1 dedup, change 2.6), the byte length (the
limit), and the content type (which parser 2.2 selects). With a direct upload, all three
arrive from the browser, and a browser can say anything.

Signed headers are a first line and not a last one: they bind *this* request to *those*
values, and they say nothing about what the object contains.

`ConfirmImportUpload` therefore records nothing and enqueues a River job. The job:

1. Sets its own tenant context from its arguments, per `CLAUDE.md`. Arguments are
   `org_id` and `batch_id` — identifiers, never file content.
2. `HEAD`s the object. A missing object fails the batch with `upload_missing`.
3. Streams it through `sha256.New()` and a byte counter, with a hard stop at
   `UploadMaxBytes + 1`. Exceeding it fails the batch with `file_too_large` and deletes
   the object.
4. Sniffs the leading bytes. `PK\x03\x04` is XLSX; anything with a NUL byte in the first
   8 KiB is rejected as binary; everything else is treated as text and left for 2.2 to
   decode. The declared type is never consulted.
5. Writes `file_sha256`, `byte_length`, `content_type` and `status = 'uploaded'` in one
   `db.InTx`, through `db.ExactlyOneRow`.

The job is idempotent on `batch_id`: a repeated confirm re-measures and writes the same
row, because reading an immutable object twice gives the same answer.

## D3 — The whole state list is declared now

**Rejected: add states as each change needs them.** Every one of 2.2, 2.3 and 2.5 would
then carry a migration that widens a `CHECK` constraint, and three migrations that edit one
constraint is three chances to disagree about what the constraint says.

**Chosen: declare all eleven states here.** The pipeline is fixed — `ARCHITECTURE.md` §4a
draws it and calls it fixed — so this is not speculation about unwritten work; it is
writing down a decision already taken. Each later change drives the states it owns and
none adds a value.

The transitions are enforced in Go, in one function in `core/internal/ingest`, not by a
trigger. A trigger would have to know which service is calling and cannot; the Go function
is tested exhaustively against the transition table.

```
awaiting_upload ─┬─▶ uploaded ─▶ parsing ─▶ parsed ─▶ validating ─┬─▶ validated ─▶ persisting ─▶ imported
                 │                                                └─▶ rejected
                 └─▶ abandoned                    any stage ──────────▶ failed
```

`rejected` is a validation outcome and carries an error report (2.3). `failed` is a defect
in us, and carries a `failure_code`. Keeping them apart matters, because one is shown to
the customer as their problem and the other is not.

## D4 — `source_kind` is immutable

A report line is computed from one source kind, and the basis label — cash or accrual — is
derived from it rather than chosen (`ARCHITECTURE.md` §5.1). If a batch's `source_kind`
could be edited after its rows were persisted, every report already printed from it would
change basis with no event recorded.

`vekst_app` therefore holds no `UPDATE` on the column. The update statement lists the
columns it sets and a test asserts that no query in `core/internal/db/query` writes
`source_kind` on an existing row. The customer's remedy is to abandon the batch and upload
again, which is correct: it is a different import.

## D5 — MinIO in the local overlay, and no bucket anywhere else

`deploy/k8s/base/kustomization.yaml` says an overlay changes configuration and never the
set of workloads, and then puts Postgres in the local overlay with the reason written
above it: no deployment overlay should inherit a datastore that has no rehearsed backup
and restore. An object store is the same argument, so it takes the same shape and the
comment is extended rather than copied.

**This leaves the change undeployable, and that is the honest state of it.** D-6 names no
host, so no bucket, no credentials and no lifecycle policy exist outside a laptop. This
change can be written, tested and merged; it cannot be demonstrated to a customer until
D-6 is answered. It is the second change to be blocked by that decision and the first for
which the block is visible.

```go
ObjectStoreEndpoint     string        // "http://minio:9000" locally; empty disables upload
ObjectStoreBucket       string
ObjectStoreRegion       string        // any value; S3-compatible stores require one
ObjectStoreAccessKeyID  string        // Secret vekst-object-store, key "access_key_id"
ObjectStoreSecretKey    string        // Secret vekst-object-store, key "secret_access_key"
ObjectStorePathStyle    bool          // true for MinIO

```

An empty endpoint follows the precedent `add-identity` set for Google credentials: `core`
still serves and `CreateImportBatch` answers with a configuration error code rather than a
nil dereference, so a developer with no credentials still gets a working stack.

## Proto

Browser-facing, served over Connect. New file `proto/vekst/v1/import.proto`. Both reviewers,
per CODEOWNERS.

**Correction made during implementation, 2026-09-13.** Every request message below gained an
`org_id` field the first draft omitted. `add-tenancy-and-rls` design D7 specifies the wire
shape this needs — `req.Msg.OrgId` resolved by `db.OrgIDForSession` before anything reaches
`db.InTx` — but no change before this one had a tenant-scoped RPC to write it against, so
nothing enforced it yet. `ImportService` is that RPC, so it is what establishes the pattern
for real: an organisation cannot be read from ambient state (there is none) or inferred from
`entity_id` alone (resolving org from entity would need the tenant context the resolution is
supposed to produce). The five messages below carry the corrected shape.

```protobuf
service ImportService {
  // Reserves a batch and returns a presigned PUT. The batch exists in
  // awaiting_upload from this moment, so an upload that never arrives is
  // visible rather than absent.
  rpc CreateImportBatch(CreateImportBatchRequest) returns (CreateImportBatchResponse);

  // The browser reports that the PUT finished. This records nothing from the
  // request: it enqueues the job that measures the object. See D2.
  rpc ConfirmImportUpload(ConfirmImportUploadRequest) returns (ConfirmImportUploadResponse);

  rpc GetImportBatch(GetImportBatchRequest) returns (GetImportBatchResponse);
  rpc ListImportBatches(ListImportBatchesRequest) returns (ListImportBatchesResponse);
}

enum SourceKind {
  SOURCE_KIND_UNSPECIFIED = 0;
  SOURCE_KIND_LEDGER      = 1;
  SOURCE_KIND_BANK        = 2;
}

enum ImportStatus {
  IMPORT_STATUS_UNSPECIFIED     = 0;
  IMPORT_STATUS_AWAITING_UPLOAD = 1;
  IMPORT_STATUS_ABANDONED       = 2;
  IMPORT_STATUS_UPLOADED        = 3;
  IMPORT_STATUS_PARSING         = 4;
  IMPORT_STATUS_PARSED          = 5;
  IMPORT_STATUS_VALIDATING      = 6;
  IMPORT_STATUS_VALIDATED       = 7;
  IMPORT_STATUS_REJECTED        = 8;
  IMPORT_STATUS_PERSISTING      = 9;
  IMPORT_STATUS_IMPORTED        = 10;
  IMPORT_STATUS_FAILED          = 11;
}

message CreateImportBatchRequest {
  string     entity_id      = 1;
  SourceKind source_kind    = 2;
  string     file_name      = 3;
  int64      declared_bytes = 4;
  string     declared_type  = 5;
}

message CreateImportBatchResponse {
  ImportBatch batch = 1;

  // Presigned. The browser PUTs the file here with exactly these headers, and
  // the store rejects anything else.
  string                       upload_url     = 2;
  map<string, string>          upload_headers = 3;
  google.protobuf.Timestamp    expires_at     = 4;
}

message ImportBatch {
  string       id           = 1;
  string       entity_id    = 2;
  SourceKind   source_kind  = 3;
  ImportStatus status       = 4;
  string       file_name    = 5;

  // int64 crosses the wire as a string in protobuf-JSON, which is what makes it
  // safe in a browser. This is a byte count and not an amount; no field in this
  // file carries money, and none may be added without the Money message.
  int64        byte_length  = 6;

  // A code, never a sentence. The client owns the words.
  string       failure_code = 7;

  google.protobuf.Timestamp created_at = 8;
}
```

No change to `proto/vekst/internal/v1/classifier.proto`. `buf breaking` has nothing to
compare against for a new file, and the rest of the workspace is untouched.

## What this touches from the invariants list

- **Tenant isolation** — a new tenant table, ordinary shape. The object key embeds `org_id`
  but the key is not the boundary: the policy is.
- **`source_kind`** — directly. D4.
- **Money and currency** — none. No amount is stored or transported by this change.
- **The classifier contract** — none.

## Rejected alternatives

| Rejected | Why |
| --- | --- |
| Bytes through a unary Connect RPC | base64 costs a third of the wire and the whole file sits in `core`'s heap, then gets written to the store anyway |
| A multipart `POST` route on `core` | Adds a second non-Connect browser surface. `CLAUDE.md` makes `/auth` an exception about transport, not about payload size |
| Trust the client's `Content-Length` and `Content-Type` | A signed header binds one request to one value; it says nothing about the object. Every number downstream would be client-supplied. See D2 |
| Store the file in Postgres as `bytea` | Removes a component and works at Demo scale. It also puts multi-megabyte objects in the same backup, the same WAL and the same connection pool as the transaction rows, and `ARCHITECTURE.md` §3 already decided the other way |
| Name the object after the uploaded file | A user-supplied name is a traversal and a collision at once |
| Add states as later changes need them | Three migrations editing one `CHECK` is three chances to disagree about it. See D3 |
| Enforce the transitions in a trigger | The legal next state depends on which stage is calling, which the database cannot see. See D3 |
| Sweep expired batches with a scheduled scan | A scan has no tenant context and would have to run outside RLS. A per-batch job carries its own `org_id`, which is what `CLAUDE.md` requires of a worker |

## Risks

| Risk | Mitigation |
| --- | --- |
| The measurement job is the only thing standing between a hostile client and every downstream number, and it is easy to skip in a hurry | The `import_batches_measured_past_upload` constraint makes the skip impossible to represent: a batch cannot be `uploaded` with a NULL sha256 |
| MinIO drifts from whatever the production store turns out to be | Only the `ObjectStore` interface is used above `core/internal/blob`; the SigV4 presigner and path-style addressing are the two places a real S3 differs, and both are exercised by the local overlay |
| The change merges and cannot be deployed, because D-6 is unanswered | Stated in the proposal as a non-goal rather than discovered at the Demo. §D5 |
| A signed URL leaks and is replayed | It is scoped to one key, one method, one length and one type, and it expires in fifteen minutes. The object it writes to belongs to a batch that is already `awaiting_upload` for one organisation |
