## Context

`eval/` holds the finished taxonomy: 101 nodes, 66 of them leaves, plus five computed
lines, generated by `eval/emit.py` from the founder's source files and measured by
`eval/run_eval.py` against 4,508 transactions. This change is the schema that receives it.

One property of that content drives every decision below. The tree is **not uniformly
tenant data**. Its top two levels are accounting structure — `NET SALES`, `OPEX >
Administration`, and the arithmetic that turns them into `GM` — and they must be identical
for every customer or reports stop being comparable and formulas stop being trustworthy.
Its leaves are specific to a business: `IT Park - membership` is a Belarusian residency
scheme, `Merch for employees` is one company's habit. 20 nodes are shared, 81 are not.

Every table this repository has created so far was one or the other. This one is both.

## Goals / Non-Goals

**Goals:** the table, its constraints, its policies, the migration that seeds it, and the
queries that read a tenant's effective tree.

**Non-goals:** rules, engine, editing, reporting, i18n of category names. Named in the
proposal.

## The data model

```sql
CREATE TABLE categories (
    id          uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
    taxonomy_version text   NOT NULL,

    -- NULL = shared by every organisation. Populated = this organisation's own.
    -- Nullable on purpose; see D1 and D2.
    org_id      uuid        NULL REFERENCES organizations (id) ON DELETE RESTRICT,
    scope       text        NOT NULL CHECK (scope IN ('global','org')),

    code        text        NOT NULL,
    parent_id   uuid        NULL REFERENCES categories (id) ON DELETE RESTRICT,
    level       smallint    NOT NULL CHECK (level BETWEEN 1 AND 5),
    name        text        NOT NULL,

    -- Report shape. Evaluated by change 4.1, stored here.
    pnl_section text        NULL,
    is_pnl      boolean     NOT NULL DEFAULT true,
    is_leaf     boolean     NOT NULL,

    -- GM, NM, CM, IBT, NI are arithmetic over other lines. A transaction can
    -- never land in one, and the engine must never be offered one as a target.
    is_computed boolean     NOT NULL DEFAULT false,
    formula     text        NULL,

    -- Payroll is known, the department is not. КНП 332 says "wages" and cannot
    -- say whose; 44 rules and 150 Kazakh rows land here. The report shows it as
    -- its own line rather than guessing a department.
    requires_allocation boolean NOT NULL DEFAULT false,

    created_at  timestamptz NOT NULL DEFAULT now(),

    CONSTRAINT categories_scope_matches_owner CHECK (
        (scope = 'global' AND org_id IS NULL) OR (scope = 'org' AND org_id IS NOT NULL)),
    CONSTRAINT categories_computed_has_formula CHECK (
        (is_computed AND formula IS NOT NULL AND is_leaf = false) OR NOT is_computed),
    -- NULLS NOT DISTINCT so two shared rows cannot share a code. Without it the
    -- uniqueness the seed relies on does not exist for exactly the rows that are
    -- shared with everybody.
    CONSTRAINT categories_code_unique
        UNIQUE NULLS NOT DISTINCT (taxonomy_version, org_id, code)
);

CREATE INDEX categories_tenant_idx ON categories (taxonomy_version, org_id);
CREATE INDEX categories_parent_idx ON categories (parent_id);
```

### Row-level security

```sql
ALTER TABLE categories ENABLE ROW LEVEL SECURITY;
ALTER TABLE categories FORCE ROW LEVEL SECURITY;

-- Read: a row that is shared, or mine. Nothing else.
CREATE POLICY categories_read ON categories
    FOR SELECT
    USING (org_id IS NULL OR org_id = app_current_org());

-- Write: only mine, and only as mine. The application can never create,
-- rename or delete a shared row -- those arrive by migration and leave by
-- migration.
CREATE POLICY categories_write ON categories
    FOR ALL
    USING (org_id = app_current_org())
    WITH CHECK (org_id = app_current_org());
```

Splitting read from write is the whole point. A single `FOR ALL` policy with
`org_id IS NULL OR org_id = app_current_org()` would let `vekst_app` rewrite `GM`'s formula
for every customer at once.

## D1 — Why `org_id` is nullable rather than two tables

**Rejected: `categories` (shared) plus `org_categories` (tenant).** It removes the nullable
column and lets each table have an ordinary policy. It also means every read of the tree is
a `UNION`, `parent_id` cannot be a foreign key because a parent may live in the other table,
and the ordering that produces a report has to be reassembled in the application. The tree
is one tree; splitting the storage does not make it two.

**Rejected: copy the shared levels into every organisation at signup.** Ordinary policy,
ordinary foreign keys, no nullable column — and a fix to the `GM` formula then reaches
nobody. The reason the top of the tree is shared is precisely so that correcting it is one
statement.

**Chosen: one table, nullable `org_id`, split policies.** The cost is that `categories` is
the first table whose isolation is not "one row, one owner", which is why D2 exists.

## D2 — What change 1.1 must sanction

This change depends on `add-tenancy-and-rls` and bends two of its rules. Both should be
agreed there rather than decided quietly here.

**(a) A tenant table with unowned rows.** 1.1's coverage test lists tenant tables lacking a
policy and fails the build. `categories` has policies, but also rows with no owner.
`deploy/db/rls-exempt-tables.txt` is the wrong home for it — that file means "carries no
tenant data", and 81 of these 101 rows do. The test needs a third state, `shared+tenant`:
a table whose policy admits `org_id IS NULL` on read and forbids it on write. Asserting the
policy *shape* is what makes the exception safe rather than a hole.

**(b) `parent_id` cannot take a composite foreign key.** 1.1 requires every referential
check between tenant tables to carry `org_id`, because a plain foreign key is a cross-tenant
existence oracle. Here the legitimate case is an organisation's leaf hanging under a *shared*
parent, whose `org_id` is NULL and therefore never equals the child's. A composite key
cannot express "the parent is shared or mine".

Proposed instead: a `CONSTRAINT TRIGGER` on insert and update asserting
`parent.org_id IS NULL OR parent.org_id = NEW.org_id`. A trigger runs as the table owner and
sees every row, so it enforces the rule the foreign key cannot state — and it closes the
oracle, because a reference to another organisation's category raises the same error whether
that category exists or not.

**(c) Seeding order, given `FORCE ROW LEVEL SECURITY`.** With `FORCE`, the owner is subject
to the policy too, and 1.1 makes `vekst_migrator` a non-superuser. Once `categories_write`
exists, the migrator inserting `org_id IS NULL` rows is denied by its own policy. Migration
005 therefore **creates the table, seeds the shared rows, and only then enables and forces
row-level security** — in that order, in one transaction. A test asserts the ordering, since
reversing it fails only on a fresh database and only for the shared rows.

**(d) Unrelated, and cheap while migration 004 is unwritten:** `memberships` has no
`entity_id`. The argument 1.1 already accepts for `entities` applies to it, the first pilot
customer is a three-country holding, and `WORKFLOW.md` §8 gives its accountant a `viewer`
seat that will want scoping. One nullable column now; a migration and a policy rewrite later.

## Queries

```sql
-- name: EffectiveTaxonomy :many
-- The tree this organisation actually sees: shared rows plus its own. RLS
-- already restricts the second half; the predicate is here for the planner and
-- for the reader, not for safety.
SELECT * FROM categories
WHERE taxonomy_version = $1
ORDER BY code;

-- name: ClassifiableCategories :many
-- What change 3.2 may target: leaves only, never a computed line. A rule that
-- points at a section or at GM is a defect the seed must not be able to express.
SELECT * FROM categories
WHERE taxonomy_version = $1 AND is_leaf AND NOT is_computed
ORDER BY code;
```

## Proto

None. This change adds no RPC: nothing browser-facing reads the taxonomy until the review
queue does, and the classifier receives it as part of `ClassifyBatchRequest` in change 3.2.

## What this touches from the invariants list

- **Tenant isolation** — directly, and in a shape the schema has not had before. §D2.
- **Money, currency, `source_kind`, the classifier contract** — none. No amount is stored
  here and no contract changes.

## Rejected alternatives

| Rejected | Why |
| --- | --- |
| Two tables, shared and tenant | Every read becomes a UNION, `parent_id` stops being a foreign key, ordering moves into the application. See D1 |
| Copy shared levels per organisation at signup | A correction to a formula then reaches nobody. See D1 |
| Put `categories` in `rls-exempt-tables.txt` | 81 of its 101 rows are tenant data. The file means the opposite |
| Composite foreign key on `parent_id` | Cannot express "parent is shared or mine". See D2(b) |
| Keep customer names as categories | 84 of the source's 158 paths were customer names. The taxonomy would then grow with every sale and be wholly per-organisation. A customer is a dimension of revenue, read from the counterparty |
| Seed from a Go fixture instead of SQL | The seed is generated and must be diffable and reviewable. SQL is both, and `eval/emit.py` regenerates it byte for byte |

## Risks

| Risk | Mitigation |
| --- | --- |
| The nullable `org_id` becomes a habit and the next table copies it without the split policies | The coverage test asserts the policy shape, not merely its presence — D2(a) |
| A shared row is seeded after `FORCE` and the migration passes on an existing database while failing on a fresh one | The ordering test in D2(c) runs against a scratch database, which is where the failure appears |
| `taxonomy_version` is stored but nothing pins it yet | 3.2 records it on every classification and 4.1 pins it on every report. Until then the column is inert, which is the cheapest time to add it |
